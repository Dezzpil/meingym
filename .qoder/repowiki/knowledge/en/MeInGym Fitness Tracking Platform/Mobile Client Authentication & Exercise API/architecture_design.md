The module is split into two layers: HTTP handlers under `src/app/api/mobile/v1/` (`auth/exchange`, `auth/register`, `me`, `exercises`, `trainings` GET/POST, `trainings/scores`, `weights` GET/POST, `records`) only verify the bearer token and validate the payload with zod, while the services in `src/mobile/` (`exchange.ts`, `register.ts`, `exercises.ts`, `trainings.ts`, `syncTrainings.ts`, `scores.ts`, `records.ts`, `weights.ts`) orchestrate business flows and reuse `src/core/*` so the mobile and web clients share one implementation of progression, scoring and records; stateless utilities live in `src/mobile/tools/`. Authentication follows a three-step pipeline — timestamp validation, HMAC signature verification over `email:timestamp`, then user lookup or creation — with all error cases surfaced through the typed `MobileAuthError` class. JWT tokens are created/verified via `jose` (HS256) in `tools/jwt.ts`, and registration additionally requires the `MOBILE_APP_TOKEN` shared secret (`x-app-token` header or `appToken` body field). Data access goes exclusively through the shared Prisma singleton from `@/tools/db`; `exercises.ts` implements cursor-based pagination with a fixed PAGE_SIZE of 20, projecting related muscle groups and images, and write batches are capped (`MAX_EXERCISES_PER_REQUEST = 50` in `scores.ts`, `MAX_BATCH_SIZE = 50` in `weights.ts`). The `tools/user.ts` layer wraps Prisma queries with a consistent `USER_SELECT` shape and uses `$transaction` to atomically create a user, default `userInfo`, and pre-seeded `equipment` with rig types and requirements. `syncTrainings.ts` persists a synchronized training and then calls `scheduleTrainingProcessing`, which hands the heavy work (records, muscles, statistics, scores) to the `trainings` Bull queue so the request stays fast.
