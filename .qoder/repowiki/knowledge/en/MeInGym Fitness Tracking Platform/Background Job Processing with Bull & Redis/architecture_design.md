The module is organized around three layers: `config.ts` centralizes Redis connection settings, queue/job name constants, and default job options (3 attempts, exponential backoff, removeOnComplete). `queues.ts` instantiates four Bull queues (`scores`, `periods`, `images`, `trainings`) bound to the shared Redis config and registers each processor against its corresponding job name. `index.ts` is the entry point that side-effects import all processors (triggering their registration), exports helper functions (`scheduleScoreCalculation`, `scheduleTrainingProcessing`, `scheduleCheckInactivePeriods`, `scheduleCleanupOrphanedImages`) for enqueueing jobs from other modules, and auto-schedules the two cron jobs on startup. The `trainings` queue is the bridge for the mobile API: `POST /api/mobile/v1/trainings` calls `scheduleTrainingProcessing`, whose processor runs `processCompletedTrainingCore` (records, muscles, statistics) which in turn enqueues `calculate-scores` on the `scores` queue. Each processor in `processors/` follows a uniform pattern: accept a Bull job, use the Prisma singleton from `@/tools/db`, call core business logic from `@/core/*`, and always `prisma.$disconnect()` in a finally block. Dependency direction is strictly inward — processors depend on `@/tools/db` and `@/core/*`, never on the rest of the app. Monitoring (`GET /api/jobs`) inspects only `scores` and `periods`, so `trainings` and `images` failures show up in worker logs only.
